# Auto Mode And Response Styles

![speech-modes-info-graph](images/speech-modes-info-graph.jpeg)

---

## The Mental Model

The key thing to tune is the **final `speech` output**, not just what the LLM first says.

In the main orchestrator flow, Jarvis gets a `raw_speech` answer and then decides how much post-processing to apply before returning final speech:

1. If a tool is on the **direct speech bypass** list, use that tool's `speech` field verbatim.
2. Else if response style is `casual`, always format for voice.
3. Else if response style is `auto`, decide based on tool type and response length.
4. Else (`detailed`), return the raw LLM answer unchanged.

Source of truth:
- `orchestrator/orchestrator_v2.py`
- `orchestrator/response_formatter.py`
- `orchestrator/router_v2.py`

This means the same final formatting layer is applied whether the turn was:
- pure Q&A with no tools
- a single tool call followed by Q&A
- multiple tool calls followed by Q&A

The main exceptions are:
- `detailed` mode
- direct speech bypass tools

## The 3 Modes

### 1. `JARVIS_RESPONSE_STYLE="casual"`

This is the strict voice-friendly mode.

What it does:
- Single-turn responses go through `_format_single_turn_casual()`
- Multi-turn responses go through `_format_multi_turn_summary()`
- Uses `JARVIS_QA_WORD_LIMIT` for Q&A/single-turn
- Uses `JARVIS_MULTI_TURN_WORD_LIMIT` for multi-turn summaries
- Tries to strip `stash://` refs, long URLs, noisy file paths, and autogenerated filenames

Best for:
- TTS/speakers
- wake-word / hands-free use
- keeping spoken answers consistently short

Important note:
- If a response is already under `JARVIS_QA_WORD_LIMIT`, `_format_single_turn_casual()` returns it as-is and does not re-condense it. The stripping rules matter most when the LLM answer is longer than the cap and gets condensed.

### 2. `JARVIS_RESPONSE_STYLE="detailed"`

This is the least opinionated mode.

What it does:
- Returns the LLM's `raw_speech` unchanged
- Does not run casual/voice condensation
- Does not apply the stash/URL/path cleanup from the casual formatter
- Allows full markdown, links, and longer explanations

Best for:
- Web UI without TTS
- debugging
- reading full research/results instead of hearing a spoken summary

This is the mode to use when you want the model's full answer, not the speech-optimized version.

### 3. `JARVIS_RESPONSE_STYLE="auto"`

This is still mostly a **voice-oriented** mode, but with one escape hatch for more detail.

What it does:
- Multi-turn responses always summarize through `_format_multi_turn_summary()`
- Pure Q&A with no tools goes through `_format_single_turn_casual()`
- Single-turn tool responses are routed by tool category and word count

Best for:
- voice/TTS when you want more detail for complex tasks
- mixed usage where most answers should stay short, but some complex answers should stay fuller

Important note:
- `auto` is not "detailed unless told otherwise"
- `auto` is better thought of as "casual/voice rules by default, except some complex single-tool outputs can stay long"

## Current Final-Speech Flow

Implementation:
- Response-style dispatch and direct-speech bypass selection: `orchestrator/orchestrator_v2.py`
- Final speech formatting helpers: `orchestrator/response_formatter.py`
- Voice prompt rules: `orchestrator/router_v2.py`

High-level flow:

```python
if use_direct_speech:
    speech = raw_speech
elif response_style == "casual":
    if turn_num > 0:
        speech = _format_multi_turn_summary(...)
    else:
        speech = _format_single_turn_casual(...)
elif response_style == "auto":
    speech = _format_auto_mode(...)
else:
    speech = raw_speech  # detailed
```

That is the easiest way to reason about tuning:
- `casual` = always voice-formatted
- `auto` = conditional voice formatting
- `detailed` = keep the LLM answer

Compatibility note:
- `orchestrator_v2.py` still exposes wrapper methods like `_format_single_turn_casual()`
- the real implementations now live in `response_formatter.py`

## Where Tool `speech` Fits

Many tools do their own parsing/formatting and return:

```json
{
  "ok": true,
  "speech": "Short human-friendly tool result",
  "data": { "structured": "payload" }
}
```

That tool-level `speech` does **not automatically** become the final user-facing answer.

Usually the flow is:
- tool returns `speech` and `data`
- orchestrator stores both in conversation context
- the LLM sees that context and produces a final `raw_speech`
- the orchestrator then applies `casual`, `auto`, or `detailed` formatting rules

Only in a few direct-bypass cases does the tool's own `speech` become final speech unchanged.

So there are really three layers to think about:

1. Tool output layer
- Tool parses raw API/script result
- Tool returns `{ok, speech, data}`

2. LLM answer layer
- LLM may use tool `speech`, tool `data`, or both
- Produces `raw_speech`

3. Final speech layer
- Orchestrator may condense/sanitize `raw_speech`
- Or may pass it through unchanged

## Example Tree Views

These are simplified decision trees for how Jarvis gets to final `speech`.

### Example A: Pure Q&A, no tools

```text
User asks question
└─ Router decides: QA, no tool call
   └─ LLM produces raw_speech
      ├─ casual
      │  └─ _format_single_turn_casual(raw_speech)
      │     └─ final speech
      ├─ auto
      │  └─ _format_auto_mode()
      │     └─ no tools used
      │        └─ _format_single_turn_casual(raw_speech)
      │           └─ final speech
      └─ detailed
         └─ raw_speech unchanged
            └─ final speech
```

### Example B: Single simple tool, short reply

Example: `get_time`, `weather`, or `crypto_price`

```text
User asks for simple live data
└─ Router calls tool
   └─ Tool runs
      ├─ parses API/result locally
      ├─ builds its own tool speech
      └─ returns {ok, speech, data}
         └─ Orchestrator stores result in context
            └─ Router/LLM decides task is complete
               └─ LLM produces raw_speech using tool result
                  ├─ casual
                  │  └─ _format_single_turn_casual(raw_speech)
                  │     └─ final speech
                  ├─ auto
                  │  └─ _format_auto_mode()
                  │     └─ SIMPLE_TOOLS match
                  │        ├─ if raw_speech <= 25 words
                  │        │  └─ raw_speech unchanged
                  │        └─ else
                  │           └─ _format_single_turn_casual(raw_speech)
                  │              └─ final speech
                  └─ detailed
                     └─ raw_speech unchanged
                        └─ final speech
```

Important:
- Even if the tool already created a nice `speech` string, the LLM may still restate it
- In the normal path, the tool `speech` is input/context, not automatically the final answer

### Example C: Single complex tool, long reply in `auto`

Example: `opencode`, `execute_bash`, `api_call`

```text
User asks for complex task
└─ Router calls complex tool
   └─ Tool returns {ok, speech, data}
      └─ Orchestrator stores result in context
         └─ LLM produces raw_speech
            ├─ casual
            │  └─ _format_single_turn_casual(raw_speech)
            │     └─ final speech
            ├─ auto
            │  └─ _format_auto_mode()
            │     └─ COMPLEX_TOOLS match
            │        ├─ if raw_speech > 75 words
            │        │  └─ raw_speech unchanged
            │        │     └─ final speech
            │        └─ else
            │           └─ _format_single_turn_casual(raw_speech)
            │              └─ final speech
            └─ detailed
               └─ raw_speech unchanged
                  └─ final speech
```

Important:
- This is the main place where `auto` can feel closer to `detailed`
- It only applies to single-turn complex-tool outputs
- It is also where the stash/URL cleanup gap exists

### Example D: Multi-tool chain, then final answer

Example: search, fetch, rank, then answer

```text
User asks for something that needs multiple tools
└─ Tool 1 runs
   └─ returns {ok, speech, data}
      └─ stored in conversation context
└─ Tool 2 runs
   └─ returns {ok, speech, data}
      └─ stored in conversation context
└─ Tool 3 runs
   └─ returns {ok, speech, data}
      └─ stored in conversation context
         └─ Router/LLM switches to QA
            └─ LLM produces raw_speech using all tool context
               ├─ casual
               │  └─ _format_multi_turn_summary(...)
               │     └─ final speech
               ├─ auto
               │  └─ _format_auto_mode()
               │     └─ turn_num > 0
               │        └─ _format_multi_turn_summary(...)
               │           └─ final speech
               └─ detailed
                  └─ raw_speech unchanged
                     └─ final speech
```

Important:
- In multi-turn work, `auto` and `casual` both collapse to a summary path
- This is why top-10 or multi-result answers can feel weaker in voice-oriented modes
- `detailed` is the path that keeps the fuller final answer

### Example E: Direct speech bypass tool

Example: `status_recap`, `generate_music`, `phone_call`

```text
User asks for task
└─ Tool runs
   └─ Tool returns {ok, speech, data}
      └─ stored in conversation context
         └─ Router/LLM switches to QA
            └─ Orchestrator checks last tool
               ├─ if last tool is in DIRECT_SPEECH_TOOLS
               │  └─ use tool's speech directly
               │     └─ skip casual/auto/detailed reformatting
               │        └─ final speech
               └─ otherwise
                  └─ normal raw_speech → formatter flow
```

Important:
- This is the true "tool speech becomes final speech" path
- It bypasses LLM rewording specifically
- It is not the same as `detailed`

## Auto Mode Logic

Implementation: `_format_auto_mode()` in `orchestrator/orchestrator_v2.py`

```python
if turn_num > 0:
    return _format_multi_turn_summary(...)

if not tools_used:
    return _format_single_turn_casual(...)

tool_name = tools_used[0]  # first tool only

if matches(SEARCH_TOOLS):
    return _format_single_turn_casual()

elif matches(SIMPLE_TOOLS):
    if word_count(raw_response) <= 25:
        return raw_response
    return _format_single_turn_casual()

elif matches(COMPLEX_TOOLS):
    if word_count(raw_response) > 75:
        return raw_response
    return _format_single_turn_casual()

else:
    return _format_single_turn_casual()
```

Important details:
- Only **single-turn** tool responses use this branching
- Only **`tools_used[0]`** is classified
- Matching is by **substring** against `tool_name.lower()`
- Unlisted tools default to the casual formatter

## Tool Categories In Auto

### SEARCH_TOOLS

Always condensed through `_format_single_turn_casual()`.

```python
SEARCH_TOOLS = [
    "search_memory",
    "semantic_recall",
    "recall",
    "search_conversations",
    "mcp_brave_search",
    "mcp_fetch",
]
```

### SIMPLE_TOOLS

Keep raw response if `<= 25` words, otherwise condense.

```python
SIMPLE_TOOLS = ["get_time", "crypto_price", "weather"]
```

### COMPLEX_TOOLS

Keep raw response if `> 75` words, otherwise condense.

```python
COMPLEX_TOOLS = ["opencode", "execute_bash", "send_webhook", "api_call"]
```

## What Is Hardcoded vs Configurable

### Configurable via env vars

In `config/cloud.env` or `config/local.env`:

- `JARVIS_RESPONSE_STYLE`
- `JARVIS_QA_WORD_LIMIT`
- `JARVIS_MULTI_TURN_WORD_LIMIT`

These drive the main condensation caps for:
- casual single-turn/Q&A
- auto-mode single-turn paths that fall into casual formatting
- all multi-turn summaries

### Still hardcoded in code/prompts

These are not env vars today:

| Value | Meaning |
|------|---------|
| `25` | Auto-mode threshold for simple tools: keep raw if `<=25` words |
| `75` | Auto-mode threshold for complex tools: keep raw if `>75` words |
| `35` | Voice/tool-confirmation brevity rule in prompts |

So:
- `JARVIS_QA_WORD_LIMIT` and `JARVIS_MULTI_TURN_WORD_LIMIT` control the main caps
- `25`, `75`, and `35` are still fixed routing/prompt constants

## The Direct Speech Bypass

There is a small exception path in the orchestrator:

```python
DIRECT_SPEECH_TOOLS = {"status_recap", "generate_music", "phone_call"}
```

If the **last tool used** is one of those, and it provides a `speech` field, Jarvis uses that tool speech directly instead of letting the LLM reformulate it.

Why this exists:
- to avoid LLMs mangling numbers
- to avoid the LLM paraphrasing specialized tool output in a worse way

This is **not the same as `detailed` mode**.

Difference:
- `detailed` = use the LLM's full answer verbatim
- direct speech bypass = use the tool's own `speech` string verbatim

So the bypass is closer to:
- "trust this tool's speech output exactly"

Not:
- "show the model's full detailed answer"

## The Known Gap In Auto Mode

This TODO is still current in code.

For complex tools in `auto` mode:
- if the raw response is `>75` words
- Jarvis returns it directly
- that means it **bypasses** `_format_single_turn_casual()`

Result:
- the final displayed text may still contain stash refs / long URLs / file paths because it skips `_format_single_turn_casual()`

Important distinction:
- this is mainly a **final text / display formatting** gap
- it is usually **not** a TTS playback gap

Why:
- standard TTS playback still runs through the shared TTS normalizer
- that normalizer strips markdown links, `http(s)` URLs, `www`, bare domains, `stash://` refs, IPs, and noisy paths before speaking

So in normal CLI/Web TTS paths:
- you may still **see** those refs in the final response text
- but you should usually **not hear** them spoken aloud

The gap is still real because:
- the displayed answer may still be noisy in that branch
- any future/custom speech path that skips the shared TTS normalizer would be exposed again

## TTS And Response Style Are Separate

At the orchestrator level, response formatting is driven by:
- `JARVIS_RESPONSE_STYLE`
- `JARVIS_QA_WORD_LIMIT`
- `JARVIS_MULTI_TURN_WORD_LIMIT`

It is **not automatically changed** just because TTS is enabled or disabled.

That means:
- if style is `detailed`, the LLM is prompted for a detailed/display-oriented answer
- if style is `auto`, the LLM/orchestrator follows the auto-mode formatting path
- if style is `casual`, the final response is always voice-formatted

Then, separately:
- if TTS playback happens, the final `speech` text is normalized for safe/natural speaking

So the normal model is:

```text
response style decides how final text is produced
└─ then TTS normalizer decides how that text is spoken
```

### Important Web UI Convenience Behavior

The Web UI adds one convenience rule on top:

- if you enable browser audio while the effective response style is `detailed`
- the Web UI automatically switches the response-style override to `auto`

Why:
- to avoid turning rich display-mode answers into bad spoken output

So:
- core orchestrator: TTS does not automatically change formatting
- Web UI client: enabling audio may intentionally switch `detailed` to `auto`

### Practical Interpretation

If TTS is disabled:
- nothing in the orchestrator automatically changes formatting just because audio is off
- you still get whatever the active response style says

If TTS is enabled:
- the active response style still controls the text-generation/formatting path
- the TTS normalizer then cleans up the final speech for playback

So yes, in principle:
- `detailed` + TTS means the LLM can still produce raw detailed output
- the LLM is not "aware of the TTS normalizer" as a separate runtime cleanup layer
- the spoken version can still be cleaner than the displayed version because TTS normalization happens afterward

### One Real Caveat

In the core orchestrator prompt, `detailed` mode tells the LLM the answer is for display/reading and that voice-output rules do not apply.

That means:
- in normal Web UI use, enabling audio usually avoids this by switching `detailed` to `auto`
- but in CLI or any custom path, you can still force `detailed` and then speak it anyway

In that case:
- the LLM is still optimizing for a rich displayed answer
- TTS normalization cleans it up afterward
- but the model itself was not prompted as if the answer would be spoken

So `detailed + TTS` works, but it is not the cleanest alignment of prompt intent and playback behavior.

## Multi-Turn Behavior

This is easy to miss but important:

If `turn_num > 0`, then:
- `casual` uses `_format_multi_turn_summary()`
- `auto` also uses `_format_multi_turn_summary()`

So in multi-turn tasks:
- `auto` does **not** preserve a long complex answer the way single-turn complex tools can
- it summarizes the whole tool chain into one final spoken answer

This is one reason Web UI users often prefer `detailed` when they want the full list, full research output, or all returned items.

---

## Tool Confirmations And The 35-Word Rule

There is still a hardcoded "tool confirmations should stay brief" rule in the prompt layer.

In the router prompt:
- tool confirmations are instructed to stay around `35` words max
- Q&A/informational answers use the active runtime Q&A cap
- this voice-output rule is skipped when response style is `detailed`

So the 35-word limit is better thought of as:
- a prompt-level brief-confirmation rule for voice/casual/auto

It is not the same thing as:
- `JARVIS_QA_WORD_LIMIT`
- `JARVIS_MULTI_TURN_WORD_LIMIT`

## Practical Tuning Advice

### If you mainly use TTS

Use:
- `casual` if you want strong consistency and predictable voice-safe output
- `auto` if you want most things concise but do not want complex single-tool answers over-trimmed

### If you mainly read results in Web UI

Use:
- `detailed`

That avoids:
- top-10 lists getting over-summarized
- search results being squeezed into short spoken summaries
- multi-turn work collapsing into one short final answer

### If you want the simplest mental model

Use this:

- `casual` = always format for speech
- `auto` = format for speech most of the time, except some long complex single-tool answers
- `detailed` = preserve the model answer

## Future Expansion Ideas

These are good candidates for a future revisit of `_format_auto_mode()` without throwing away the current voice-first behavior.

### 1. Stop Looking Only At `tools_used[0]`

Current behavior:
- single-turn `auto` classifies only the first tool name

Why this is brittle:
- the first tool may not represent the final answer shape
- a lightweight lookup tool may run first, but the final response may really be dominated by a later display-heavy tool

Safer future options:
- classify by the **last tool used**
- classify by **all tools used**
- let tools expose a small metadata hint such as `prefer_detailed`, `voice_safe`, or `display_heavy`

Low-risk path:
- start by checking `tools_used[-1]` as a secondary fallback when `tools_used[0]` looks too generic

### 2. Split "Display Richness" From "Speech Friendliness"

Right now `auto` is doing two jobs:
- deciding how detailed the final text should be
- deciding how voice-friendly the final answer should be

That works, but it mixes display and speech concerns.

A cleaner future model would be:
- `response_style` or `display_style` decides how rich the returned text should be
- TTS normalization / speech-style rules decide how the text is spoken

That would help Web UI no-TTS and Web UI with TTS coexist more cleanly.

### 3. Add A Lightweight Post-Processing Step For Long Complex Auto Responses

Current behavior:
- long single-turn complex responses in `auto` return raw text directly

Possible improvement:
- keep the response detailed
- but run a small non-condensing cleanup pass for display hygiene

Examples:
- strip or soften raw `stash://` refs
- shorten very long raw URLs in display text
- simplify noisy filesystem paths when they are not user-relevant

This would preserve detail without routing everything back through `_format_single_turn_casual()`.

### 4. Make Multi-Turn Auto Less Aggressively Summarizing In Display-Heavy Contexts

Current behavior:
- once `turn_num > 0`, `auto` always uses `_format_multi_turn_summary()`

That is great for voice, but weaker for:
- top-10 lists
- search-heavy research
- multi-source comparisons
- workflows where the final answer should show more than a single spoken summary

Possible future directions:
- add an "expanded auto" path for Web UI display-heavy contexts
- use tool/result metadata to decide whether multi-turn should summarize or preserve more structure
- allow a larger multi-turn display answer while still keeping TTS playback concise via the TTS normalizer

### 5. Let Tools Tell Auto Mode What Kind Of Output They Produce

Instead of relying only on hardcoded tool-name buckets, tools could eventually declare small formatting hints such as:

- `voice_brief`
- `display_heavy`
- `number_sensitive`
- `prefer_direct_speech`
- `prefer_detailed_if_long`

That would make the behavior less patchy than:
- one-off bypass lists
- substring matching on tool names
- ad hoc word-count thresholds

### 6. Revisit The Direct Speech Bypass As A Formal Strategy

The current bypass list likely exists for real reasons:
- LLM number mangling
- tools that already produce high-quality speech
- cases where rewording hurts clarity

Future cleanup could formalize this into a tool capability rather than a hardcoded set:
- tool says "my `speech` is authoritative"
- orchestrator decides whether to trust it directly or only in voice-first modes

That would preserve the benefit while making the behavior easier to understand and extend.

### 7. Keep The Good Parts

Even if `_format_auto_mode()` gets revisited later, these parts are still worth preserving:

- `casual` as the strict voice-first mode
- `detailed` as the display/debugging mode
- `auto` as the pragmatic middle ground
- TTS normalization as the final speech-safety layer

The goal probably is not to make `auto` fully generic.
The goal is to keep it useful for voice while making it less underpowered for richer display contexts.

---

## Bottom Line

If your goal is "make it feel right":

- `casual` is the strict voice/TTS mode
- `auto` is still voice-first, just more permissive for some single-turn complex outputs
- `detailed` is the reading/debugging mode where you stop fighting the speech formatter

And for current code:
- yes, the env vars matter
- yes, `25 / 50 / 35` are still hardcoded
- yes, the complex-tool TODO is still real
- yes, the direct-speech bypass is a separate patch-path and not the same thing as `detailed`
